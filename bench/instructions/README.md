# Instruction gate

Instructions, allocations and bytes per iteration of the runtime's hot workloads, exact, against a baseline per target: `x86_64-unknown-linux-gnu.txt` and `aarch64-unknown-linux-gnu.txt` ([docs/performance-gates.md](../../docs/performance-gates.md)). CI's `instructions` jobs (`ubuntu-24.04` and `ubuntu-24.04-arm`) run the check on every push and pull request; nothing needs to run locally.

```sh
python3 bench/instructions/run.py --check                       # Linux with Valgrind: this target's baseline
python3 bench/instructions/run.py --check bench/instructions/aarch64-unknown-linux-gnu.txt --allocations-only   # any OS, natively
python3 bench/instructions/run.py --write /tmp/before.txt       # a local baseline
python3 bench/instructions/run.py --jitter 5                    # are the counts exact here?
```

## How it counts

The driver (`crates/otter-lang/examples/bench_gate.rs`) runs one workload for N iterations and prints the allocations and bytes the process requested, through a counting allocator. `run.py` runs every workload at N and at 2N under Cachegrind, in parallel, and records `(count(2N) - count(N)) / N` for each column: process start, parsing, compose, instantiation and teardown cancel, leaving one iteration's steady-state cost.

The workloads:
- `vm/CASE/WIDTH`: the VM suite's 25 cases at widths 8, 64 and 256, generated by `bench/vm-execution/workloads.py` without the clock reads (N = 1000);
- `entity/100`: a steady tick of 100 entity instances (`bench_instances`; N = 100 ticks);
- `depth/1`, `depth/16`: 100 instances suspending and resuming through 1 and 16 nested calls (`bench_depth --progress`; N = 100 ticks);
- `table/CASE`: `bench_tables`' six VM cases (N = 1000);
- `reload`: a preserving reload of an edited function, then two ticks (N = 10 cycles);
- `object/assign`, `object/seq`, `object/table`: a host object copied between locals 8 times, into a 4-element sequence, into a 4-key record (N = 1000; docs/host-requirements.md H1);
- `service/lookup`: 8 service lookups at activation by a host leaf (N = 1000; H3).

Every workload checks the work it did (results, iteration and resume counts) and fails otherwise. The workload definitions are shared with the examples (`otter_core::bench`) and the matched VM suite, not copied.

Columns: `ir` (instructions), `allocs` and `bytes` are gated: the check fails on any rise. `d1_misses`, `ll_misses` and `mispredicts` come from Cachegrind's cache and branch simulators with a fixed geometry; they model a generic machine, so they are recorded and reported, not gated.

## Exactness

Every column is exact: five full runs give identical numbers. Two things had to be fixed for that:
- the runtime's own hash maps used randomly seeded SipHash, so compose probed differently in each run, and that fixed cost differed between the N and 2N runs; they use fixed keys now (`otter_core::hash`);
- Cachegrind probes the cache geometry from the CPU it starts on, which on a hybrid CPU differs between performance and efficiency cores; `run.py` passes a fixed one.

If a count starts to vary, `--jitter` shows which; find the source rather than adding a tolerance.

## Baselines and environments

Instruction counts depend on the exact Valgrind and C library build as well as the source: Valgrind substitutes its own `memcpy` and `malloc`, and libc code is counted. The baseline's header records the toolchain, target, C library and Valgrind, and `--check` refuses a baseline from another environment (`--ignore-environment` overrides; `--allocations-only` compares only allocations, which do not depend on it).

The committed baselines are CI's (`ubuntu-24.04` and `ubuntu-24.04-arm`, their packaged Valgrind): one per target, because instruction selection and register allocation differ. After an intended change, take the baselines the jobs measured:

```sh
gh run download RUN -p 'instructions-*' -D /tmp/fresh   # each job uploads the baseline it measured
cp /tmp/fresh/*/*.txt bench/instructions/
```

and say in the commit why the counts changed, as for hot-asm and the compose baseline.

On a Linux machine, a change can also be compared locally against its base:

```sh
git switch --detach BASE && python3 bench/instructions/run.py --write /tmp/before.txt
git switch -   && python3 bench/instructions/run.py --check /tmp/before.txt
```

The whole set takes about 5 seconds on 24 cores.
