## Implemented

- **Core** (`otter-core`): compose once, instantiate many (shared immutable `Compiled`, small per-instance `State`), a content-keyed compose cache with recorded dependencies, frame slots with definite-initialization checks, exactly-once cleanup through shared lifecycle helpers.
- **One scheduler:** `Mesh` runs instances on an iterative, directly resumable engine (`stackless/`: generation-tagged frame arena, central control continuations, iterative initialization and cleanup, a per-mesh call-depth limit). The same engine runs on native, wasm (WASI) and ESP-IDF. The stackful prototype scheduler was deleted after the M4 gate.
- **VM:** compose-selected builtin instructions with a borrowed accumulator; arithmetic near 1.x parity, collections 3 to 4x slower ([runtime overview](runtime-performance-overview.md)).
- **I/O** (`otter-io`): `Http.Get` (URL, timeout, headers, bytes, full response, retry with backoff) on a shared Tokio runtime, with cancellation verified; the `FS.*` shards on its blocking pool, scoped by the host's `FsAccess` service.
- **Text with dependencies** (`otter-text`, 2026-10-16; in the `otter` command's catalog): `Regex.Match`, `Regex.Search`, `Regex.Replace` on the Rust `regex` engine (linear time). A constant pattern compiles once at compose into the shared compiled output, and an invalid one is a compose diagnostic naming the `regex` argument; a pattern from a variable compiles at activation, and each instance keeps the last one; every pattern is bounded (1 MiB compiled, 1 MiB lazy-DFA cache) since models may write them. `Hash.Sha2-256`, `Hash.Sha1`, `Hash.Md5`, `Hash.Blake2-128`, `Hash.Blake2-256`, `Hash.Blake3` (Bytes), `Hash.XXH3-64` (Int) and `Hash.XXH3-128` (Bytes, canonical order), of a String's UTF-8 bytes or of Bytes. `UUID` (version 4, the hyphenated String) and `NanoID(size)`, from the system's generator, declaring the `random` effect. Tested natively and on WASI (standard vectors, catastrophic-looking patterns, variable patterns, located errors); not in the ESP32 firmware.
- **Values and types:** a 32-byte `Var` (f32 `Float2/3/4` behind 16-aligned wrappers), string-keyed sorted tables as struct tables (interned `Shape`, slot-indexed `Take`) or sorted vectors behind the opaque `Table`, fixed/open table types, unions, `Never`, one acceptance rule, `Bytes` ([values-and-types.md](values-and-types.md)). `Var` drops and copies its storage by hand (an inline tag check, storage out of line, as 1.x's `destroyVar`/`destroyVarSlow`), so adding a variant does not change the VM's code; native builds align branch targets (`.cargo/config.toml`) so benchmark comparisons do not depend on code placement ([runtime overview](runtime-performance-overview.md), lesson 7).
- **Metadata:** every catalog shard has a `ShardDesc`; structured diagnostics with occurrence paths; JSON catalog, describe and search.
- **Frontend** (`otter-lang`, `otter-cli`): hand-written parser with spans and recovery, lowering to wire definitions, `check --json`, `run`, `watch`, state-preserving hot reload ([embedding.md §5](embedding.md#5-warm-sessions-and-hot-reload)), tools loaded and called by a host (`Tool`, `otter tool`, [embedding.md §6](embedding.md#6-tools)). `@include` (each file once per program) and `@read` (text or `bytes: true`) read files at load time through a host-replaceable reader (`Files`: the filesystem with the CLI's `-I`, or files in memory for devices and tests); diagnostics name the file they are in, and `watch` reloads when an included or read file changes ([embedding.md §3](embedding.md#3-the-catalog-and-scripts)).
- **ESP32:** firmware example linked and booted in QEMU for three chips in CI; no physical-board run claimed.

**VM-level steps (2026-10-07, `51525a6` and `7bac245`).** The reviews' fixes brought the entity workload to parity with the gate; the next commit makes the engine take fewer steps. A stateless, non-recursive call to a straight-line body, a `Repeat` whose body and `until` flow are straight-line, and a `When` or `While` whose predicate and action are straight-line are VM instructions (`VmCall`, `VmRepeat`, `VmBranch`): they run inside the caller's segment, on the kept frame's locals for a call, without an engine step, and a loop checks every site in its body is ready before it starts so a body never runs halfway and then needs the engine (a site is not ready on the first call and after a reload, when the frame path enters it). A call site is prepared and entered in the same step, and a child flow that is leaf code (no shard activation, site, loop, branch or constructor) runs inside the composite's dispatch with its completion dispatched in the same step. Measured with runs interleaved against the baselines (`bench_instances 1000`, release, aarch64): gate 99 µs per tick and 1.66 KiB per instance, e706cfb 101 µs and 1.68 KiB, now 98 µs and 1.68 KiB; `bench_depth --progress` at depth 1/4/16/32: e706cfb 81/81/85/87 ns per instance tick, now 78/81/82/82. Two variants were measured and rejected on the way: evaluating a child flow in the step (its scans and completion round trip cost more than the steps it saved) and inlining the dispatch match into the step (5 percent worse on the entity workload). `7bac245` then inlined the common `Take` reads (the generic runner had grown past the inliner's budget for `take_value`, which the VM suite showed as a 20 to 50 percent slowdown on the take cases). **Flat control flow (2026-10-07, after `7bac245`).** The VM's fixed cost per loop iteration was twice 1.x's (10 ns against 5) because a `Repeat` iteration re-entered `inline::run`, whose prologue dominates a short body. Compose now lowers `Repeat`, `While`, `When` and `If` to flat code in the parent flow (`ComposeCtx::flatten`): their children's nodes and instructions are merged into the parent, with `Jump`, `JumpIf`, `JumpIfNot` and `LoopTest` instructions and hidden frame slots (the saved input, a loop counter) for the composite's own control. An iteration or a branch is a jump inside one run, the composite has no frames or continuation of its own, and a child that must suspend keeps its node: the engine activates it where the run stops and continues the flat code after it. This drops the one-instruction-per-node identity: `CompiledFlow::pc_nodes` maps every instruction to the node it stands for (`NO_NODE` for control instructions), and the engine indexes states and nodes through it. The VM-level `VmRepeat` and `VmBranch` instructions of `51525a6` are gone, replaced by this; `VmCall` stays (a callee addresses another frame's locals), as do the frames of `Match`, `Once`, `Sub`, `Maybe`, `Conditions` and calls. Measured before the commit, interleaved with the `7bac245` binaries on a loaded laptop: the entity workload 88 µs per tick against 101, with 1.30 KiB of heap per instance against 1.68 (the `When`'s frames are gone); `bench_depth --progress` 38 to 40 ns per instance tick against 84 to 86 (the bottom `While` is flat); the VM suite's fixed cost per iteration 4.3 ns against 10.3, below 1.x's 5.2. `scratch_slots` and fresh per-iteration locals cover hidden slots like any ordinary local. A side finding worth knowing when reading benchmark numbers on this machine: under background load (macOS media indexing) single processes run at about 1.75× their usual time for their whole life, presumably scheduled on efficiency cores; comparisons are only valid interleaved, and a 32-byte value alignment was tried as a fix and rejected (it coincided with the load dropping, and costs the entity workload 15 percent through 64-byte instructions).

**Inlined calls (2026-10-07, after `aae5c01`).** A call to a stateless, non-recursive, straight-line body of at most 24 instructions (`INLINE_BUDGET`) with no call site of its own is inlined at compose (`ComposeCtx::flatten`, the `Call` arm): the callee's instructions are spliced into the caller's code with their local slots rebased onto hidden slots of the caller's frame, arguments are bound by instructions (a constant or a caller binding, then a `Set`), the input flows through the accumulator (saved to the callee's input slot only when the body reads `input` by name or arguments clobber the accumulator), and the callee's nodes join the caller's for the instruction-to-node map. A callee's own inlined calls come along, `INLINE_DEPTH` levels deep: eight on hosts, where an inlined level is a call that costs nothing at run time, and two on ESP-IDF, where each level of a chain holds a copy of the code and dependency lists below it (unbounded, a 24-deep chain's compile peaked 90 KiB higher, 256 against 167 KiB with a counting allocator, and exhausted the C3 and the classic ESP32 in the frontend suite's chain test; at two the peak is 170 KiB). The device gets the setting, not the design: host performance is the default, as with `MAX_FLOW_DEPTH` and the device fixtures. A body over the budget, with a call site, with `Keep` slots, stateful, recursive or suspending stays a `VmCall` or a frame. Inlined calls enter no invocation frame, so they do not count toward `max_call_depth`. Measured interleaved against `aae5c01` binaries: the VM suite's function call per element (`do-int`) 11 / 62 / 208 ns at widths 8 / 64 / 256 against 183 / 1,394 / 5,710 (1.x 74 / 587 / 2,487); entity and depth unchanged.

*Inlined sites and §11 (written into §11 itself).* An inlined callee's code is part of its caller's body, so the caller depends on it: `Dep::Inlined` is recorded (and the callee's own inlined dependencies with it), a body comparison counts it (`same_body` still ignores plain `Dep::Function`), and the edit takes effect when the recomposed caller is next entered, not at the callee's next call inside an in-flight caller. A *wire* whose body inlined a changed function is neither restarted nor cut: an instance not started yet, or between two iterations, takes the candidate's body at once; a looped instance in the middle of an iteration finishes it on its body and moves onto the new one at its end (`Instance::next_body`); a run of a wire that does not loop finishes on its body and is not listed. Moving is `Engine::rebase`: every compilation of a flow records the node ranges its inlined calls brought (`CompiledFlow::lowered`, allocated only for a flow that has any), the remaining nodes are the flow's own and must pair up by shard, control and call target between the two bodies (`rebasable`, checked by `validate_reload`; a stateless call site may stand where the other body inlines the call), and each own node keeps its state: leaves their native state, composites their flags (`Once`), call sites their kept frames (components with their `Keep` slots, cached invocations) with the body their frames run selected again at the next entry. Only the nodes of inlined calls start fresh, and locals are laid out for the new body with `Keep` slots carried by name and type. So no state is lost and nothing needs admission under `ResetPolicy::Reject`; the report lists such wires under `swapped`. A spawned wire's framed callees are recorded in its spawner's restart dependencies (it embeds the spawned body) but do not swap it: only `Dep::Inlined` does. Admission still checks every function the wire's sites were composed with, and functions whose own definition changed are admitted first, so a rejection names the edited function. Callees that keep their frames (they suspend, hold state or recurse) follow §11 unchanged, as `an_in_flight_parent_selects_the_newest_framed_callee_at_its_next_entry` pins.

*Value lifetimes of calls and hidden slots.* A call's values (input, arguments, locals) end when it returns or fails, so a collection the caller passed in is uniquely owned again and the caller's next mutation of it is not a copy: an inlined call ends with `Op::Clear` on each slot it used that may hold a heap value (a scalar-typed slot needs nothing, so a numeric helper costs no instruction), a flattened composite clears its saved input at its exit the same way, a code run that ends otherwise (a failure, `Stop`, `Return`, `Restart`) clears every such slot of its flow (`Lowered::released_slots`), and a call on a kept frame (framed or `VmCall`) unsets the locals that do not persist at its exit instead of at its next entry. A cached stateless invocation that fails to start cleans up the leaves that attempt instantiated (`revive_invocation`), like a first build.

## Deviations from 1.x

The earlier list (syntax, numbers, tables, `Push`, `Match`, `Once`, `check`) is in [history.md](history.md#deviations-from-1x). Since then:
- **No `$0`, `$1`, `$i`.** 1.x's `ForEach` and `Map` exposed the element, key, value and index as implicit variables, which shadow each other in nested loops and are declared nowhere. In 2.0 a sequence's element is the block's input, a table's entries arrive as `{key value}` (a struct table), and an index comes from a separate `Seq.Enumerate` that yields `{index value}`; no flag changes the input's shape. `$<digit>` is a lexer error with help pointing at the block's input ([metaprogramming.md §1](metaprogramming.md#1-the-ladder)).
- **`#( )` is pure** ([metaprogramming.md §2.1](metaprogramming.md#21-semantics)): 1.x ran arbitrary shards while loading, effects included.
- **`@include` includes a file once per program** wherever it is named again; 1.x included it again unless `Once: true`, which in 2.0 would always fail (a function cannot be declared twice). No `Fallback:` file. `@read` reads while loading and records the file for reloads; there is no `@env`.
- **Dates are UTC with a `strftime` subset.** 1.x's `Date.Format` and `Date.Parse` took any chrono `strftime` format, `Date.Parse` read time zone offsets and, without a format, guessed among common ones (RFC 3339, ISO 8601 and others), and `Date.Format` defaulted to `%a %b %e %T %Y`. In 2.0 both take `%Y %m %d %H %M %S %%` and literal characters, in UTC (no time zone database on every target), with the default `%Y-%m-%d %H:%M:%S` for both; another specifier is a compose error, and parsing matches the format exactly, never guessing. Names, weekdays, fractions and offsets come back when a ported script needs them.
- **JSON is only plain JSON** (host-requirements.md §3). 1.x's `ToJson`/`FromJson` had `Pure: false`, a typed envelope (`{"type": ..., "value": ...}`) that round-tripped every value kind, bytes and vectors included; 2.0 has only the plain mapping, as 1.x's default `Pure: true` did, with Ints and Floats kept apart in both. Unlike 1.x's plain mode, float vectors are written as arrays rather than rejected.
- **Regex is the Rust `regex` dialect** (host-requirements.md §3), not C++ `std::regex` (ECMAScript): no lookaround or backreferences, matching in linear time, so a pattern a model writes cannot hang a wire; `\w`, `\d` and `\s` are Unicode-aware. A pattern can be a variable (1.x took only a literal), and patterns are size-limited. `Regex.Search` searches the whole input once, left to right: 1.x searched again in the rest of the string after each match, so `^` matched again there and an empty match (`a*`) looped forever. `Regex.Replace` uses Rust's replacement syntax: `$0` (not `$&`) is the whole match, `${1}x` separates a group from following letters, and ECMAScript's `` $` `` and `$'` do not exist. `Regex.Match` anchors the parsed pattern, so `a|ab` matches `"ab"` whole, as 1.x's `regex_match` did.
- **Hashes take a String or Bytes**, not 1.x's sequences of them (join first with `Bytes.Join` or `String.Join`). `Hash.XXH3-64` outputs an Int (1.x: 8 little-endian bytes) and `Hash.XXH3-128` 16 bytes in XXH3's canonical big-endian order (1.x: the low then the high half, each little-endian), so `ToHex` prints what `xxhsum` prints. `Hash.Sha1`, `Hash.Md5` and `Hash.Blake3` are new; 1.x's `Hash.Sha2-512`, `Hash.Sha3-*`, `Hash.Keccak-*` and the legacy `Hash.XXH-64`/`-128` are not ported yet.
- **`UUID` outputs the standard hyphenated String.** 1.x output the 16 bytes as an `Int16` vector, formatted by `UUID.ToString` (unhyphenated by default) and converted by `UUID.ToBytes` and `UUID.Convert`; 2.0 has no `Int16`, and those three are not ported. `NanoID`'s `size` is a literal from 1 to 1024 (unbounded in 1.x).
- **File access is a host service, not a parameter.** 1.x's `FS.*` shards took `BasePath:` and `FollowSymlinks:` per call, so a script chose its own confinement; in 2.0 the host's `FsAccess` decides, and a path leaving its directory through a link is always denied. Without one, paths are unrestricted, as in 1.x without `BasePath:`.
- **`FS.Write` does not create missing directories** (1.x did): writing into a missing directory fails, so a typo cannot scatter a new tree; `FS.CreateDirectories` creates one. `FS.Read` without `bytes: true` fails on contents that are not UTF-8 (1.x returned them as an invalid string), and has no `ChunkSize:` or `MaxSize:` yet.
- **`FS.Iterate` lists one level by default** (`recursive: false`; 1.x recursed by default) and sorts its output (1.x gave directory order); an entry that cannot be read fails the listing (1.x skipped it with a warning). No `UseIgnore:`, `Hidden:` (hidden entries are listed) or `FollowLinks:` (links are listed, never entered).
- **`FS.Copy` takes `overwrite:`** instead of 1.x's `Behavior:` enum (`Fail`, `Skip`, `Overwrite`, `Update`); a directory copied into itself is an error. **`FS.Rename` outputs the new path** (1.x output the old one, which no longer exists). `FS.Exists` is new (1.x had only `IsFile`/`IsDirectory`). `FS.Extension`, `FS.Filename`, `FS.Parent` and `FS.Join` behave as in 1.x (the extension keeps its dot); `ReplaceExtension`, `RelativeTo`, `Absolute`, `IsAbsolute`, `Normalize`, `Size`, the write-time shards, `Is`/`IsAny`/`IsNotAny`, `Watch` and the file dialogs are not ported.
- **`Http.Get` retries only transient failures** (no connection, a timeout, a body cut short and, without `full-response`, 408, 429, 500, 502, 503, 504) and reports the last error with the attempt count; 1.x retried every failure, a 404 included, and reported a bare "Request failed". `backoff` may be fractional. `full-response` still retries transport errors (1.x documented it as disabling retries) and joins a repeated header's values with `, ` (1.x kept one).
- **The §3 core shards** (host-requirements.md §3, second Done paragraph):
  - `String.CleanUTF8` reads a byte string (a String is always valid UTF-8 here), replacing invalid sequences with U+FFFD; 1.x took a string and replaced them with NUL, which cut the text short. `String.FromCodePoints` rejects what is not a Unicode scalar value; 1.x wrote any Int.
  - `Reverse` reverses a string by characters; 1.x reversed its bytes, breaking multi-byte characters.
  - The sequence shards name their variable `variable` (1.x: `Collection`, `Target`, `Name`) and take no table `Key`; `Clear` empties sequences and tables whose type lists no keys, and refuses others at compose (1.x passed silently over other kinds, and refused fixed tables). `Extend`, `AppendTo` and the rest check the element type at compose (1.x's `Extend` did not).
  - `Remove` outputs and assigns the kept elements; its predicate sees the sequence as it was when Remove started, and an error in it leaves the variable unchanged (1.x removed in place as it went). No `Join:` or `Unordered:`.
  - `IndexOf` looks for an element when the item's type can be one, and for a run of elements otherwise; 1.x treated every sequence item as a run, so it could not find a sequence element. An empty run is an error (1.x matched at 0). No `predicate:` yet.
  - `Cond` takes its pairs as arguments, `Cond({pred} {action} ... passthrough: false)`, not as one sequence `Cond([...])`; without `passthrough`, a Cond where no predicate is true outputs its input (1.x output the last predicate's `false`). No `Threading:`.
  - `Msg`'s `level:` is a string (`"warning"`), as Otter has no enums; lines other than `info` are prefixed with their level, and nothing names the wire. No `Name:` or `Raw:`.
  - `Assert.Is` and `Assert.IsNot` compare as `Is` does (1 equals 1.0; 1.x compared types strictly), refuse types that can never be equal at compose, and have no `Break:` (a debugger breaks on the activation error instead).
  - `HexToBytes` is also `FromHex`, mirroring `ToHex`. `Time.EpochLocal` is not ported (no time zone database on every target).

## Open items outside the golden path

- **`inline::run` is layout-fragile.** Unrelated edits to the interpreter loop move the whole VM suite by tens of percent through block order and register choice ([lessons](runtime-performance-overview.md#lessons-from-the-vm-optimization-work), point 6). The current code is the best measured; before the next change to `run`, make its hot path predictable by construction, and A/B every edit on the whole VM suite.
- **A flow-taking function is inlined all or nothing.** One shard without a VM form in its body (or its block) keeps the call framed, and each element then runs the block in a frame: about 5 times a loop written in place (`examples/bench_flow_params.rs`, the `framed` variant), against parity inlined. `Count` got a VM form (2026-10-10), so the usual `ForEach` is inlined; `check --json` says for each call site how it runs and why it is not inlined. The durable fix keeps an inlined inner loop when only the setup around it cannot be.
- **Review follow-ups not yet done (2026-10-10 reviews):** evaluate an `@const` once rather than at every read; `check --limits esp32`; count traversal size in a cached result's usage; meter `Take` with a string key; include frame memory in the device heap bound.
- **VM coverage.** A call whose callee suspends, holds a `Keep`, is recursive, has a call site of its own or exceeds the inlining budget takes the `VmCall` or frame path, as do `Match`, `Once`, `Sub`, `Maybe` and `Conditions` (a leaf child flow of theirs still runs inside the dispatch); the first call through a non-inlined site and the first after a reload take the frame path too. Flattening the remaining composites needs a jump table (`Match`), a hidden flag (`Once`) and a handler table for `Maybe` (an error between two instruction indices resumes at a handler); inlining a body that itself calls needs its call sites' operands rebased too. Per 1.x, constructors (`Table.Make`, sequence literals built per iteration), pushes to a shared sequence and a function call per element remain slower (1.1× to 2.5× at width 256, [runtime-performance-overview.md](runtime-performance-overview.md#golden-path-refresh-2026-10-07)).
- **Compose stack per nesting level** is about 6 KiB natively for function bodies (the `Do` path was 3.5 KiB), so ESP-IDF keeps `MAX_FLOW_DEPTH` at 24; the next step is attributing the per-level temporaries (the call-site compose alone is 2.4 KiB) or composing iteratively (golden path §6.3's later item).
- The type registry never frees (shapes included; the soak test records 2 shapes and 2 types per reload that introduces a new record shape); scoped registries are needed for long `watch` sessions.
- The compose cache is unbounded.
- Recursive types; objects, services, module ports and the C API, whose decisions are proposed in [host-requirements.md](host-requirements.md) (gaps found by surveying a large production 1.x host, awaiting decision; priorities in its §7); browser wasm; graphics and physics.
- The external host is porting its shards to 2.0 ([embedding.md](embedding.md)); it must move to the opaque `Table` API (M1) and, with this checkpoint, drop the mesh type parameters from `check`, `run` and `Session`.
