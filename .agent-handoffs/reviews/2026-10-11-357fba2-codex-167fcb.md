## F1 — P1 Honor pending termination before allowing the target to finish successfully
- Location: `crates/otter-core/src/stackless/runtime.rs:594` (tick activation), `:883` (finish), `:909` (drain); `crates/otter-core/src/wire_instance.rs:128` (request).
- Evidence: request only sets an atomic and increments the counter; it never fires the target waker. Tick performs every eligible activation before draining requests, and finish publishes the activation's outcome without consulting the pending request. Drain skips already-finished instances. Thus a request made while a target is still running can be discarded completely, even when made before its first activation. Independently reproduced all three cases under both `PollEveryTick` and `OnNotify`:
  1. Host starts a non-looped wire `[Const(7)]`, gets its completion, calls `request(Request::Stop)` before the first tick, then ticks. Actual outcome is `Completed(Int(7))`, expected `Stopped`.
  2. Script equivalent: `@wire(child {7}) Spawn(child) = w Pause() Stop(w) Wait(w)`. The parent requests Stop before the child's first activation in tick 2, yet Wait succeeds with 7 instead of failing `wire-stopped`.
  3. Script equivalent: `@wire(child {7}) Spawn(child) Pause()`. Tick 2 finishes the owner first, requesting child cancellation, but the child then runs and publishes `Completed(7)` instead of `Cancelled`.
- Impact: stopped/cancelled work still executes its body and can report success. Child effects can occur after the owner ends. This violates H5's termination outcomes and structured ownership; the documented implementation additionally claims requests wake targets and are honored on reaching a woken instance, neither of which exists in this snapshot. Current-state and runtime comments do describe end-of-tick draining, but even that policy needs an explicit rule for a request already pending when normal completion is published; it does not currently guarantee that the target ends Stopped/Cancelled.
- Suggested direction: implement and document one consistent cancellation boundary, handling pending requests before target activation/wake filtering as H5 specifies, plus the end-of-pass tree drain. Define request-versus-completion ordering for concurrent host requests rather than silently losing requests that already preceded activation. Preserve cleanup-before-publication and the distinct Stop/Cancel results. Add all three reproductions in both wake modes and a ready/woken async target case; existing stop tests use sleepers that cannot complete during the extra activation.

## F2 — P1 Drain owned-child cancellations before returning from reload installation
- Location: `crates/otter-core/src/stackless/runtime.rs:433` (`Mesh::install_revision`, including the later rebase-failure termination path).
- Evidence: install_revision finishes removed/replaced owners, which only requests cancellation of their children. It never calls drain. A retained child's definition passes the reload compatibility check, so it remains live after its owner is cancelled. Independent repro: install looped `child=[Pause]` and looped `owner=[Once(Spawn(child)), Pause]`; start owner and tick twice; retain a handle to the child; create a revision with the same child and owner changed to `[Pause]`, with owner ID in `removed`; validate and install. Immediately afterwards child's completion outcome is `None`, expected `Some(Cancelled)`. No simultaneous host thread is needed.
- Impact: reload returns with orphaned work and resources still active. If the host does not tick again they remain indefinitely; if it does, F1 permits another activation before cancellation, including external effects or successful completion. H5 requires cancellation of the whole owned tree in the same pass when an owner ends for any reason. Mesh::cancel already explicitly drains its tree; reload needs equivalent semantics.
- Suggested direction: settle cascading termination requests during installation, including those caused by rebase failures, before returning control to the host. Add reload tests with owned children/grandchildren whose own definitions remain compatible, and verify completion/cleanup immediately without an intervening tick. The existing reload test exercises only independently host-spawned instances.

## F3 — P2 Validate timeout deadline arithmetic before registering a waiter
- Location: `crates/otter-core/src/stackless/shards.rs:97`–`:103`; accepted durations originate in `crates/otter-core/src/shards/instances.rs::compose_wait`.
- Evidence: `Duration::try_from_secs_f64(1.0e19)` succeeds, so `Wait(w timeout: 1.0e19)` composes. On Linux, `Instant::now() + duration` then panics with `overflow when adding duration to instant`. This happens after completion.wait inserted the waiter and before a Registration value was constructed/stored. Consequently no Registration::drop removes that waiter. Independent repro used a looped sleeper target, a separate non-looped waiter with that timeout, and one tick: waiter ended `Failed(Activation("panic in activation: overflow when adding duration to instant"))`; target.waiter_count remained 1, even after cancelling the already-finished waiter, expected 0 on failure.
- Impact: valid-by-compose script input causes an activation panic and leaks a stale registration until the target ends. Repeated failed waits against a long-lived target accumulate registrations. With aborting panics the same unchecked overflow can terminate the process; that consequence is inferred, not device-tested.
- Suggested direction: use checked deadline arithmetic and return a normal error before inserting a registration, or represent elapsed time without overflowing Instant. Ensure every path after insertion owns an RAII registration immediately. Test oversized finite timeouts and registration counts after rejection/failure in addition to the existing zero-timeout test.
